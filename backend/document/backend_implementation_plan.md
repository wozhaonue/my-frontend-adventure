# 前端冒险（Backend）详细实施计划（面向前端 AI 开发者）

## 0. 文档定位与执行方式

本计划基于以下两份设计资料整理：

- backend_design.md
- backend_tech_stack.md

本计划目标：

- 用最小实现成本搭建可上线的后端基础能力。
- 按“先能跑，再完善”的顺序交付。
- 每一步都附带可执行的验证测试，避免“以为完成”。
- 面向前端背景开发者，尽量减少后端术语门槛。

执行规则：

- 严格按顺序执行，禁止跳步。
- 每完成一步，必须先做验证测试，测试通过后再进入下一步。
- 如测试不通过，先修复当前步，不要叠加新改动。

---

## 1. 里程碑与范围

### 里程碑 A：基础工程可启动

- 完成 TypeScript + Express 工程骨架。
- 完成环境变量、日志、安全中间件、错误处理基础层。

### 里程碑 B：数据层可用

- 完成 PostgreSQL + Prisma 模型、迁移、种子数据。
- 完成 Redis 连接与健康检查。

### 里程碑 C：核心业务可用

- 完成用户登录验证码流程（请求验证码、轮询登录状态、微信回调处理）。
- 完成技术列表、关卡增删改查、关卡重排、AI 生成与导入。
- 完成 90 天未登录自动注销任务。

### 里程碑 D：质量与交付

- 完成接口级测试与关键流程回归。
- 完成 Docker 化与部署前检查。

## 2. 分步实施指令（每步含验证）

### 步骤 01：初始化后端项目目录

操作指令：

- 在 backend 目录下创建 src、prisma、document 之外的业务子目录，结构按技术栈建议中的目录组织。
- 确保目录至少包含 config、middlewares、modules、jobs、libs。
- 在 modules 下预建 users、wechat、techs、levels、ai 子目录。

验证测试：

- 打开 backend 目录，人工核对目录结构是否完整。
- 检查是否不存在重复命名目录（例如 user 与 users 并存）。

通过标准：

- 目录结构与建议结构一致，后续文件可直接落位。

### 步骤 02：初始化 Node.js 与 TypeScript 工程配置

操作指令：

- 初始化后端包管理配置。
- 添加运行、开发、构建、测试相关脚本入口。
- 添加 TypeScript 基础配置，确保可编译到独立产物目录。

验证测试：

- 执行依赖安装并运行类型编译。
- 观察是否生成编译产物目录且无类型错误。

通过标准：

- 项目可完成一次完整编译，且无阻塞错误。

### 步骤 03：安装最小可用依赖

操作指令：

- 按技术栈文档安装运行时依赖与开发依赖。
- 仅安装文档中已推荐依赖，避免超前引入复杂框架。

验证测试：

- 检查包清单，确认包含 Express、Prisma、PostgreSQL 驱动、Redis、JWT、bcrypt、Zod、node-cron、安全中间件、Pino、测试工具。
- 重新执行安装，确认无冲突与缺失提示。

通过标准：

- 依赖安装稳定，重复安装无异常。

### 步骤 04：建立环境变量分层方案

操作指令：

- 设计本地开发、测试、生产三套环境变量清单。
- 明确数据库连接、Redis 连接、JWT 密钥、服务端口、日志级别、外部回调配置项。
- 建立缺失变量时的启动失败机制。

验证测试：

- 在缺少关键变量时启动服务，确认服务拒绝启动并给出明确错误。
- 在变量完整时启动服务，确认服务正常运行。

通过标准：

- 配置错误可被快速发现，避免带病启动。

### 步骤 05：搭建应用入口与健康检查接口

操作指令：

- 创建应用入口文件与服务启动文件，分离应用创建和监听端口逻辑。
- 提供健康检查接口，用于确认服务是否在线。

验证测试：

- 启动服务后访问健康检查接口。
- 验证返回状态为成功且响应时间稳定。

通过标准：

- 服务可启动，可通过健康检查确认在线状态。

### 步骤 06：接入基础中间件链路

操作指令：

- 按顺序接入 cors、helmet、请求体解析、请求日志。
- 配置基础跨域策略，仅放行前端需要的来源。

验证测试：

- 使用浏览器从前端地址访问后端接口，验证无跨域阻塞。
- 检查响应头，确认安全头已生效。

通过标准：

- 前端可访问后端，安全头与跨域策略同时生效。

### 步骤 07：建立统一错误处理机制

操作指令：

- 统一业务错误、参数错误、系统错误的响应格式。
- 在全局错误处理中间件中屏蔽敏感信息，保留可定位字段。

验证测试：

- 手动触发一个参数错误与一个内部错误。
- 验证返回结构一致、状态码正确、敏感信息未泄露。

通过标准：

- 所有异常都能被统一接管，接口错误可读且安全。

### 步骤 08：建立请求校验层

操作指令：

- 为所有写入型接口预留 Zod 校验入口。
- 约定校验失败的统一响应规范。

验证测试：

- 向任一写入接口提交缺字段请求与字段类型错误请求。
- 验证均被拦截且不会进入业务层。

通过标准：

- 非法输入在入口被阻断，数据库不出现脏写入。

### 步骤 09：配置 Prisma 与数据库连接

操作指令：

- 初始化 Prisma 工程并连接 PostgreSQL。
- 建立数据库连接健康检查。

验证测试：

- 执行 Prisma 基础命令确认可连接数据库。
- 在数据库不可用时启动服务，验证报错可读。

通过标准：

- 数据库连接稳定，故障时可快速定位。

### 步骤 10：落地 Users、Technologies、Levels 三张核心表

操作指令：

- 按设计文档完成三张表字段定义与关系约束。
- 为唯一字段、索引字段、排序字段添加必要约束。

验证测试：

- 执行迁移后检查表结构。
- 验证唯一约束与外键约束按预期生效。

通过标准：

- 数据模型与设计一致，约束有效。

### 步骤 11：创建固定技术字典种子数据

操作指令：

- 初始化 HTML、CSS、JavaScript、TypeScript、Vue、React 六项固定技术数据。
- 约束种子重复执行时不产生重复记录。

验证测试：

- 连续执行两次种子写入。
- 验证技术总数仍为六条，且标识稳定不变。

通过标准：

- 技术字典可重复初始化且幂等。

### 步骤 12：接入 Redis 并建立缓存命名规范

操作指令：

- 接入 Redis 客户端并在服务启动时完成连接检查。
- 设计验证码、登录状态、轮询状态三类键命名规则与过期时间。

验证测试：

- 写入测试键并读取回查。
- 等待过期时间后验证键自动失效。

通过标准：

- Redis 可用，短期状态具备自动回收能力。

### 步骤 13：实现用户请求登录验证码接口

操作指令：

- 实现“生成 4 位纯数字验证码”接口。
- 将验证码状态写入 Redis，初始状态为待验证，设置过期时间为 5 分钟。
- 对该接口增加速率限制（如：1 分钟内同一 IP 最多请求 5 次），防止刷接口。

验证测试：

- 连续请求多次，验证验证码格式正确且状态初始化成功。
- 高频请求触发限流，验证限流响应符合预期。

通过标准：

- 验证码可生成、可缓存、可防刷。

### 步骤 14：实现前端轮询登录状态接口

操作指令：

- 实现按验证码查询登录状态接口（前端建议 3 秒轮询一次）。
- 未验证时返回“等待中”；已验证时签发单 JWT（有效期 7 天）并返回用户信息，随后立即删除 Redis 中的验证码（一次性消费）。
- 成功签发后更新用户最后登录时间。若用户 `is_deactivated` 为 true，自动重置为 false。

验证测试：

- 使用未验证验证码查询，返回等待状态。
- 将验证码状态手动改为已验证后再次查询，返回令牌与用户信息。
- 检查数据库中最后登录时间被更新。

通过标准：

- 轮询状态流转完整，登录成功后可拿到令牌。

### 步骤 15：实现微信回调基础验签与消息接收

操作指令：

- 实现微信回调 GET 接口，完成微信初次配置的签名校验。
- 实现微信回调 POST 接口，完成来源校验与 XML 消息解析。
- 仅处理文本消息中的验证码，其余消息类型快速返回。

验证测试：

- 发送合法回调样例，验证可被接收。
- 发送非法来源或非法结构样例，验证被拒绝。

通过标准：

- 回调入口安全可控，非法请求不会进入业务流程。

### 步骤 16：实现微信回调中的用户绑定逻辑

操作指令：

- 在回调处理中根据 OpenID 查找用户，不存在则静默注册。
- 将“验证码 → 用户已验证”状态写回 Redis。
- 返回登录成功类消息给微信侧。

验证测试：

- 使用新 OpenID 回调，验证数据库出现新用户。
- 使用已存在 OpenID 回调，验证不重复创建用户。
- 验证对应验证码状态被更新为已验证。

通过标准：

- 用户绑定与验证码确认逻辑正确，重复回调可安全处理。

### 步骤 17：实现 JWT 鉴权中间件

操作指令：

- 实现令牌解析与用户身份注入。
- 令牌仅携带最小必要字段。
- 对无令牌、过期令牌、非法令牌返回统一鉴权错误。

验证测试：

- 分别用三类无效令牌访问受保护接口，验证均被拒绝。
- 使用有效令牌访问受保护接口，验证通过。

通过标准：

- 鉴权边界清晰，受保护接口不可越权访问。

### 步骤 18：实现获取当前用户信息接口

操作指令：

- 提供获取当前登录用户资料接口。
- 若用户已被注销，返回明确错误并拒绝继续访问。

验证测试：

- 有效令牌访问，返回用户资料。
- 将用户状态改为已注销后再访问，验证被拦截。

通过标准：

- 用户状态校验生效，注销账号无法继续使用系统。

### 步骤 19：实现获取技术列表接口

操作指令：

- 提供技术列表只读接口，固定返回六个技术模块。
- 响应顺序保持稳定，便于前端直接渲染。

验证测试：

- 多次请求该接口，验证数量、顺序、关键字段一致。

通过标准：

- 技术列表稳定可预测，满足前端固定导航需求。

### 步骤 20：实现获取指定技术下关卡列表接口

操作指令：

- 按用户与技术双条件查询关卡。
- 按 order_index 升序返回。

验证测试：

- 准备乱序测试数据后请求接口。
- 验证返回顺序严格按 order_index 排列。

通过标准：

- 同一技术下关卡顺序稳定正确。

### 步骤 21：实现新增关卡（含 AI 导入）接口

操作指令：

- 支持向指定技术追加关卡。
- 明确 order_index 分配策略：自动追加或按传入值插入。
- 对输入内容做结构校验，拒绝不合法关卡内容。

验证测试：

- 新增合法关卡后，列表总数增加且顺序符合预期。
- 提交非法内容时被校验拦截，数据库无新增。

通过标准：

- 新增路径稳定，非法输入无法写库。

### 步骤 22：实现删除关卡接口

操作指令：

- 按关卡标识删除当前用户可操作的目标关卡。

验证测试：

通过标准：

### 步骤 23：实现关卡重排接口（事务保障）

操作指令：

- 接收该技术下所有关卡的 ID 与新顺序数组（格式如 `[{id, order_index}]`），进行全量批量更新 `order_index`。

验证测试：

通过标准：

### 步骤 24：实现 AI 生成关卡接口（仅生成不落库）

## 3. 前端 AI 开发者执行提示（降低后端门槛）

- 每次只做一个接口，不要并行改多个模块。
- 每完成一个接口，立即做“成功场景 + 失败场景”双测试。
- 任何写库接口都先做输入校验，再做数据库操作。
- 涉及顺序重排、批量更新时必须使用事务思维。
- 遇到“状态类需求”（验证码、轮询）优先放 Redis，不要放 PostgreSQL。
- 遇到“长期业务数据”（用户、关卡）放 PostgreSQL，不要放 Redis。
- 先保证接口稳定，再考虑性能优化。

## 4. 完成定义（Definition of Done）

满足以下条件，判定后端实施完成：

- 30 个步骤全部执行完毕且逐步测试通过。
- 登录验证码流程端到端可用。
- 技术列表与关卡管理全部接口可用。
- AI 生成与导入流程可用，且生成接口不落库。
- 90 天自动注销任务可验证生效。
- 自动化测试可稳定重复通过。
- 容器化部署在新环境可一次拉起并联调通过。
